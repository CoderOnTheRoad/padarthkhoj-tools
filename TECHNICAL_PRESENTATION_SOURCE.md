# QE Studio: Technical Architecture and Code Logic

## Purpose

This document is technical source material for generating a presentation about QE Studio. It explains the repository structure, architecture, data flow, algorithms, input/output handling, visualisation system, testing strategy, and limitations.

## One-Sentence Description

QE Studio is a browser-based scientific workflow application for Quantum ESPRESSO and electronic-structure analysis. It reads scientific files locally in the browser, parses them into structured JavaScript objects, applies domain-specific algorithms, renders structures or plots, and exports QE inputs, CIFs, CSVs, XLSX workbooks, PNGs, ZIP archives, and JSON templates.

## High-Level Architecture

~~~text
User input
    |
    v
Page controller in src/pages
    |
    v
Reusable parser/calculation in src/lib
    |
    v
Normalized data object or calculation result
    |
    +--> Three.js structure viewer
    +--> Canvas plot
    +--> HTML tables and status panels
    +--> Text, CSV, XLSX, PNG, ZIP, or JSON export
~~~

The application is primarily client-side. In normal browser workflows, files are read with the FileReader API and are not uploaded to an application server.

The shell is deliberately generic. Workflow-specific markup is generated by page classes rather than permanently embedded in the HTML file.

### src/main.js

This is the browser entry point and lightweight router.

Responsibilities:

- Define the global appState object.
- Register page IDs and page metadata.
- Connect navigation controls.
- Destroy the active page before loading another page.
- Clear and repopulate page-content.
- Update the sidebar, topbar, and page title.
- Dispatch theme, visual-style, and text-size events.
- Persist comfort settings in localStorage.

The shared state contains values such as:

~~~javascript
{
  cifData,
  cifFilename,
  selectedAtom,
  pendingProtocol,
  generatedInput,
  generatedInputs
}
~~~

Navigation lifecycle:

~~~text
sidebar click
  -> navigate(pageId)
  -> destroy previous page
  -> clear page-content
  -> instantiate selected page class
  -> call render()
  -> bind events and create viewers
~~~

This lifecycle prevents multiple page instances from retaining DOM listeners or animation loops.

### src/pages

The page directory contains user-facing workflow controllers. A page generally:

1. Creates its HTML.
2. Connects file inputs and buttons.
3. Reads user data.
4. Calls reusable functions from src/lib.
5. Stores local workflow state.
6. Updates tables, charts, or viewers.
7. Starts downloads or transitions to another workflow.

Pages are orchestration code. They should not contain the core scientific equations or complex file-format algorithms.

## CIF Parsing: src/lib/cifParser.js

### Purpose

Parse a CIF structure into cell parameters, atoms, symmetry-expanded positions, fractional coordinates, and Cartesian coordinates suitable for visualisation and QE workflows.

### Main function

~~~javascript
parseCIF(text)
~~~

### Input

A CIF file represented as a text string.

### Output model

~~~javascript
{
  cell: { a, b, c, alpha, beta, gamma },
  atoms: [
    { sym, fx, fy, fz, x, y, z }
  ],
  mat,
  symmetry
}
~~~

### Algorithm

1. Split the CIF into lines.
2. Search for unit-cell lengths and angles.
3. Scan loop_ blocks.
4. Identify a symmetry-operation loop if available.
5. Identify the atom-site loop.
6. Read labels, element symbols, fractional coordinates, and occupancy.
7. Parse algebraic symmetry operations.
8. Apply every symmetry operation to every primitive atom.
9. Wrap transformed fractional coordinates into the [0,1) interval.
10. Convert fractional positions into Cartesian coordinates.
11. Deduplicate primitive atoms using a fractional-coordinate tolerance.
12. Deduplicate expanded atoms using a Cartesian-distance tolerance.
13. Return the expanded structure and symmetry metadata.

### Symmetry formula representation

A symmetry operation such as:

~~~text
-x+1/2, y, z
~~~

is represented as three affine equations:

~~~text
x' = xC*x + yC*y + zC*z + constant
y' = xC*x + yC*y + zC*z + constant
z' = xC*x + yC*y + zC*z + constant
~~~

This allows the parser to evaluate symmetry operations without hard-coding every possible operation.

### Coordinate transformation

The fractional-to-Cartesian transformation uses a lattice matrix derived from a, b, c and the three cell angles. The matrix supports non-orthogonal cells, including triclinic cells.

### Duplicate handling

There are two deduplication passes:

- Primitive atoms are compared in fractional space.
- Symmetry-expanded atoms are compared in Cartesian space.

If primitive atoms overlap, occupancy is used to decide which atom record survives.

### CIF export

The export function writes:

- Cell lengths
- Cell angles
- Atom labels
- Element symbols
- Fractional coordinates

Coordinates are formatted to a fixed number of decimal places.

## CIF Generator: src/lib/cifGenerator.js

### Purpose

Generate multiple structural variants by substituting selected atom types.

### CIF parsing

This module preserves raw lines so that substitutions can be applied without completely rebuilding the original CIF. It supports:

- Fractional coordinates
- Cartesian coordinates
- Cell parameter extraction
- Quoted tokens
- Atom labels and type symbols

### Combination algorithm

~~~javascript
generateCombinations(configs)
~~~

The function calculates the Cartesian product of all active substitution sets.

Example:

~~~text
Atom 1: Cu or Ag
Atom 2: O or S
~~~

Generated combinations:

~~~text
(Cu,O)
(Cu,S)
(Ag,O)
(Ag,S)
~~~

The number of structures is:

~~~text
N = product of the number of substitutions for each active atom
~~~

### Applying substitutions

applyCombination():

1. Create an atom-ID-to-element mapping.
2. Copy the original CIF lines.
3. Replace the atom type-symbol column.
4. Update the atom label prefix.
5. Add a provenance comment containing the source and substitutions.
6. Return the new CIF text.

### ZIP export

exportZIP():

1. Create a JSZip archive.
2. Add each generated CIF file.
3. Generate a Blob.
4. Trigger a browser download.

## CIF Symmetry: src/lib/cifSymmetry.js

This module connects crystallographic information with Quantum ESPRESSO cell notation.

### Lattice classification

findLattice() compares cell lengths and angles using tolerances. It classifies the cell as one of the common crystal systems:

- Triclinic
- Monoclinic
- Orthorhombic
- Tetragonal
- Hexagonal
- Rhombohedral
- Cubic

Tolerances are important because CIF values are floating-point approximations and should not be compared using exact equality.

### Bravais-lattice mapping

findIbrav() maps space-group information and lattice system to the QE ibrav integer.

Examples include simple cubic, face-centred cubic, hexagonal, and general triclinic representations.

### celldm generation

buildCelldm() generates QE celldm parameters. Depending on ibrav, these values represent:

- Overall lattice scale
- Ratios between lattice lengths
- Cosines of cell angles

### Cell-vector generation

buildCellVectors() converts crystallographic lengths and angles into three Cartesian lattice vectors.

### K-point estimation

computeKPoints() estimates a reciprocal-space sampling mesh from real-space dimensions and a requested spacing. Shorter real-space dimensions normally require denser reciprocal-space sampling.

## CIF-to-QE Conversion: src/lib/cifToQE.js

### Main function

~~~javascript
cifToQE(cifText, coordMode, decimals)
~~~

### Full CIF tokenizer

parseCIFFull() handles:

- Comments
- Quoted strings
- Semicolon-delimited multiline values
- Key-value pairs
- Loop columns
- Loop rows
- Missing values represented by . or ?

The parser stores loop data separately so that atom-site rows can be identified reliably.

### Conversion algorithm

1. Tokenize the CIF text.
2. Parse cell parameters.
3. Locate the atom-site loop.
4. Identify element, fractional, and Cartesian columns.
5. Use Cartesian coordinates when present and suitable.
6. Convert fractional coordinates to Cartesian coordinates when requested.
7. Format ATOMIC_POSITIONS with either crystal or angstrom units.
8. Collect the unique element species.
9. Return generated text and metadata.

The result includes:

~~~javascript
{
  text,
  atomCount,
  species,
  cellStr,
  sg
}
~~~

## Quantum ESPRESSO Input Generation: src/lib/qeGenerator.js

### Purpose

Generate QE input decks from a structure and a selected computational protocol.

### Main functions

~~~javascript
generateQEInput()
generateDOSWorkflow()
generateBandsWorkflow()
generateChargeWorkflow()
generateBaderWorkflow()
generateVibrationalWorkflow()
generatePWWorkflow()
~~~

### Protocol-driven generation

The protocol controls:

- QE calculation type
- Control settings
- System settings
- Electronic settings
- Ionic settings
- Cell settings
- K-point settings
- Required output files

Protocols include SCF, relaxation, variable-cell relaxation, DOS, band structure, charge density, Bader preparation, and vibrational calculations.

### Input-generation algorithm

1. Receive the selected protocol.
2. Receive parsed cell and atom data.
3. Look up pseudopotentials.
4. Look up atomic masses.
5. Generate the CONTROL namelist.
6. Generate the SYSTEM namelist.
7. Generate the ELECTRONS namelist.
8. Add IONS for ionic relaxation.
9. Add CELL for variable-cell relaxation.
10. Generate ATOMIC_SPECIES.
11. Generate ATOMIC_POSITIONS.
12. Add CELL_PARAMETERS if the cell is explicit.
13. Generate K_POINTS.
14. Return formatted QE input text.

### Multi-file workflows

DOS workflows can require several sequential input files, such as:

~~~text
SCF input
NSCF input
DOS input
PDOS input
~~~

These files are returned as a collection and displayed as tabs in the input editor.

## Quantum ESPRESSO Output Parser: src/lib/qeParser.js

### Main function

~~~javascript
parseQEOutput(text)
~~~

### Extracted fields

The parser can extract:

- Calculation type
- Total-energy history
- Force history
- Pressure history
- SCF iterations
- Convergence status
- Job completion status
- Error messages
- Initial structure
- Relaxation steps
- Final structure
- Initial cell vectors
- Final cell vectors

### Line scanning

The parser scans line by line and applies regular expressions to known QE output patterns, including:

~~~text
! total energy = ... Ry
Total force = ...
P = ...
iteration # ...
convergence has been achieved
JOB DONE.
~~~

It stores histories rather than only the final value. The final energy, force, and pressure are taken from the final valid item in each history.

### Calculation-type detection

The parser first looks for explicit calculation metadata such as scf, relax, or vc-relax. If it is absent, it infers the type using evidence such as:

- Multiple CELL_PARAMETERS blocks
- Final-coordinate blocks
- BFGS relaxation messages
- QE program headers

### Unit normalization

QE can use Bohr, Angstrom, alat, and crystal coordinates. The parser normalizes these using:

~~~text
1 Bohr = 0.529177210903 Angstrom
~~~

### Relaxation-step extraction

For each CELL_PARAMETERS card:

1. Read three lattice vectors.
2. Interpret their unit.
3. Search forward for the corresponding ATOMIC_POSITIONS card.
4. Read atom labels and coordinates.
5. Store the geometry step.

The final-coordinate block is preferred when QE prints Begin final coordinates and End final coordinates.

## QE Input Reconstruction and Patching: src/lib/qeInputGenerator.js

This module provides two strategies.

### Strategy A: Patch the original input

~~~javascript
patchInputFile(originalIn, parsedOutput)
~~~

The original input is preserved and only structural sections are changed.

For atomic positions:

1. Locate ATOMIC_POSITIONS.
2. Replace the old atom rows.
3. Preserve the coordinate unit.

For variable-cell calculations:

- If ibrav is not zero, update relevant celldm or A/B/C values.
- If ibrav is zero, replace the CELL_PARAMETERS card.

The module knows which celldm values are relevant for each ibrav.

### Strategy B: Reconstruct the input

~~~javascript
buildIN(P, useInitial)
~~~

This creates a new QE input from parsed parameters. It can use either the initial or final structure.

It generates:

~~~text
&CONTROL
&SYSTEM
&ELECTRONS
&IONS
&CELL
ATOMIC_SPECIES
CELL_PARAMETERS
K_POINTS
ATOMIC_POSITIONS
~~~

### QE syntax highlighting

hlCode() classifies lines as:

- Comments
- Namelists
- Namelist terminators
- QE cards
- Element rows
- Numbers
- Keywords
- Values

hlDiff() additionally highlights structural lines that differ from the original input.

## Bader Charge Analysis: src/lib/baderAnalysis.js

### Inputs

- Bader ACF.dat
- QE input or VASP POSCAR/CONTCAR structure
- Optional core or valence-electron information

### Algorithm

1. Parse ACF atom records.
2. Parse the reference structure.
3. Extract atom elements and positions.
4. Match structure atoms to Bader records by order or available identifiers.
5. Determine reference valence electrons.
6. Calculate net charge.
7. Attach charge and volume data to atom records.
8. Display charge values in the viewer.
9. Export a table or workbook.

The charge relation is:

~~~text
net charge = reference valence electrons - Bader electron population
~~~

### Workbook export

The workbook includes per-atom results, element information, charge values, Bader volumes, and summary metadata. It is produced as an XLSX ZIP/XML package.

## Bond Detection: src/lib/bonding.js

Bond detection is geometric and heuristic rather than quantum-mechanical.

### Algorithm

1. Iterate through candidate atom pairs.
2. Check element-pair selection rules.
3. Calculate the displacement vector.
4. Include periodic translations when a lattice is available.
5. Calculate Euclidean distance.
6. Compare distance against a threshold.
7. Store accepted bonds.
8. Render each bond as a Three.js line segment.

When bonds are re-rendered, old geometries and materials are disposed to reduce GPU-memory usage.

## Intermediate Placement: src/lib/intermediateMaker.js

### Direction conversion

The module converts azimuth and elevation angles into a normalized three-dimensional direction vector. It also supports the inverse operation, converting a vector back to angles.

### Placement algorithm

1. Select an active catalyst atom.
2. Identify the intermediate's adsorption anchor.
3. Determine the adsorption direction.
4. Rotate the intermediate according to the requested orientation.
5. Translate the intermediate so its anchor is positioned near the active catalyst atom.
6. Return transformed Cartesian coordinates.

### Collision evaluation

evaluatePlacement() calculates distances between intermediate atoms and catalyst atoms. Any distance below the configured minimum is reported as a collision.

evaluatePlacementVolume() checks whether atoms enter a spherical region around the active site.

### Placement suggestions

suggestPlacementSpheres():

1. Generates candidate points around the active atom.
2. Translates each candidate by a chosen centre distance.
3. Evaluates the candidate geometry.
4. Rejects candidates with collisions.
5. Returns a limited list of valid candidates.

### CIF output

buildIntermediateCIF() merges the catalyst structure and transformed intermediate atoms into a new CIF.

## PDOS Analysis: src/lib/pdosAnalysis.js

### Supported concepts

PDOS records can identify:

- Atom number
- Element
- Orbital
- Spin channel
- Energy values
- DOS values

The module also supports VASP DOSCAR and POSCAR-style data.

### Parsing algorithm

1. Parse the filename for atom, element, orbital, and spin metadata.
2. Parse the file header.
3. Identify the energy column.
4. Identify orbital or spin columns.
5. Parse numeric rows.
6. Store a normalized PDOS record.

### DOSCAR parsing

For VASP DOSCAR:

1. Read the DOSCAR header.
2. Extract the Fermi energy and grid information.
3. Read total DOS.
4. Read partial DOS when available.
5. Map orbital columns.
6. Return normalized records.

### Atom selection

A string such as:

~~~text
1,3,5-8
~~~

is converted into:

~~~text
1, 3, 5, 6, 7, 8
~~~

The parser validates ranges, removes duplicates, and returns a predictable sorted selection.

### Summation algorithm

1. Filter records by selected atom.
2. Filter by species and orbital.
3. Validate compatible energy grids.
4. Apply the requested Fermi-energy shift.
5. Add DOS values at corresponding energy points.
6. Return the combined DOS result.

Mathematically:

~~~text
combined_DOS(E_i) = DOS_1(E_i) + DOS_2(E_i) + ... + DOS_n(E_i)
~~~

## Orbital Metrics: src/lib/orbitalMetrics.js

### Purpose

Calculate numerical descriptors from DOS or PDOS channels.

### Formula compiler

Supported syntax includes:

- Numbers
- Column references
- Addition
- Subtraction
- Multiplication
- Division
- Parentheses

Example:

~~~text
B + C * 2
~~~

The implementation follows a shunting-yard-style approach:

1. Tokenize numbers, references, and operators.
2. Validate the sequence of operands and operators.
3. Apply operator precedence.
4. Convert to postfix representation.
5. Evaluate postfix tokens with a stack.

Errors include empty formulas, missing operators, unmatched parentheses, unknown columns, division by zero, and non-finite results.

### Derived columns

addDerivedColumn():

1. Compile the formula.
2. Resolve referenced columns.
3. Evaluate the formula for every energy row.
4. Append the result as a derived channel.
5. Store null when the calculation is invalid.

### Integrated DOS area

The module uses the trapezoidal rule:

~~~text
area = sum over i of:
       (E_i - E_(i-1)) * (DOS_i + DOS_(i-1)) / 2
~~~

### Band centre

The band centre is:

~~~text
band centre =
integral(E * DOS(E) dE) /
integral(DOS(E) dE)
~~~

Both integrals use the trapezoidal rule.

### XLSX generation

The workbook is constructed directly as an Office Open XML ZIP package containing workbook XML, worksheet XML, relationships, and content-type metadata.

## Vibrational Thermodynamics: src/lib/zpeTs.js

### Input parsing

Frequency input can be separated by spaces, commas, semicolons, or newlines. The parser returns valid numerical values and a separate invalid-token list.

### Validation

The module excludes:

- Non-numeric values
- Negative frequencies, treated as imaginary modes
- Zero-frequency modes
- Non-positive temperatures

### Equations

For each frequency:

~~~text
frequency_Hz = frequency_THz * 10^12
~~~

~~~text
x = h*nu / (kB*T)
~~~

~~~text
occupation = 1 / (exp(x) - 1)
~~~

~~~text
ZPE = h*nu/2
~~~

~~~text
U_thermal = h*nu/(exp(x)-1)
~~~

~~~text
S_vib = kB * [x/(exp(x)-1) - ln(1-exp(-x))]
~~~

~~~text
F_vib_correction = ZPE + U_thermal - T*S_vib
~~~

The module includes safe handling for large x values so exponential overflow does not produce invalid results.

## Validation and Error Handling

Validation exists at parser, calculation, and UI levels.

Examples:

- Missing CIF atom-site loops produce errors.
- Missing cell parameters prevent fractional-to-Cartesian conversion.
- Invalid frequency tokens are reported separately.
- Negative and zero vibrational modes are excluded.
- Incompatible DOS energy grids are rejected before summation.
- Invalid formulas produce errors or null metric values.
- Missing source columns are reported.
- Invalid custom-pathway JSON is rejected.
- QE convergence failures and error messages are collected.

The general design principle is explicit failure or visible warning instead of silently producing scientifically ambiguous output.

## Security and Resource Management

Dynamic HTML values are escaped through src/lib/html.js before insertion into the DOM.

The application also manages resources:

- Three.js geometries are disposed when replaced.
- Three.js materials are disposed when replaced.
- Event listeners are removed during page destruction.
- Temporary download URLs are revoked.
- Uploaded files remain local to the browser during normal use.

## Important Design Decisions

### Client-side processing

Scientific files are processed locally in the browser. This reduces data-transfer requirements and avoids sending research files to a remote server.

### Reusable scientific modules

Parsers and algorithms are isolated from UI pages. The same calculation can therefore be reused, tested independently, and connected to multiple interfaces.

### Normalized internal representations

Different input formats are converted into common structures such as:

~~~javascript
{
  energy: [],
  channels: {},
  atoms: [],
  vecs: [],
  metadata: {}
}
~~~

This allows plotting and export code to work independently of the original file format.

### Versioned templates

DOS templates, orbital-metric templates, and custom pathway templates include explicit format and version information. This supports validation and future compatibility.

### Numerical stability

The code uses:

- Geometric tolerances
- Clamping before inverse trigonometric functions
- Safe exponential limits
- Division-by-zero checks
- Finite-number validation
- Energy-grid compatibility checks

## Known Limitations

- Very large files may be limited by browser memory.
- Some parsers depend on expected layouts from QE, VASP, Bader, and PDOS tools.
- Geometric bond detection is heuristic and is not a quantum-mechanical bond-order calculation.
- Pseudopotential selection depends on static mappings and still requires user verification.
- Generated QE inputs require scientific review before production calculations.
- The browser application prepares and analyses files but does not execute Quantum ESPRESSO itself.
- Numerical output is only as reliable as the input file format, units, and metadata.

## Technical Closing Statement

QE Studio is a modular scientific data pipeline. Each workflow follows the same pattern: raw domain-specific text is parsed, converted into a normalized internal model, processed by a focused algorithm, rendered for inspection, and exported into a format suitable for computational chemistry or further analysis. The separation between pages, reusable libraries, visual components, static scientific data, and tests allows the project to support many workflows without duplicating the core scientific logic.
